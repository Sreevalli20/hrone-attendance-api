# DECISIONS.md

1. **Indexes.** I created a unique index on `employees.emp_code` to enforce uniqueness at the database level, which prevents duplicate employee creation even under concurrent requests. For attendance logs, I created a compound unique index on `(emp_code, date)` to handle the punch-in race condition - this ensures exactly one request succeeds while others get 409. I also added supporting indexes on `date`, `status`, `department`, and `joined_on` to ensure the analytics aggregations use IXSCAN instead of COLLSCAN on large datasets. I considered adding a partial index for `punch_out: null` to optimize punch-out queries, but rejected it because the compound index on `(emp_code, date)` with the query filter is sufficient.

2. **Punch-in race.** When two identical punch-in requests arrive simultaneously, both attempt to insert a document with the same `(emp_code, date)`. The compound unique index guarantees that MongoDB will allow exactly one insert to succeed and throw a DuplicateKeyError for the other. My code catches this exception and returns 409 Conflict for the loser. This approach is atomic and doesn't require check-then-insert logic, which would be vulnerable to race conditions.

3. **Ties.** If two employees are tied on late minutes at the cutoff limit, my leaderboard returns both. I apply the limit after ranking, so all employees with `rank <= limit` are included. This means if three employees tie at rank 5 and limit is 5, all three are returned. This is correct per the spec: "limit applies after ranking" and ties share a rank.

4. **Headcount.** Department summary uses a separate aggregation on the `employees` collection to count all employees with `joined_on <= month_end`, regardless of whether they have attendance logs. This count is then joined with the attendance stats from the logs collection. This ensures employees with zero logs are still counted in headcount, as required by R9.

5. **One thing you would change** if this had to serve 100x the data: I would add a materialized view or pre-aggregated collection for daily department statistics, computed by a scheduled job. Currently, the department trend endpoint queries all attendance logs for the date range and computes headcounts per day, which would become slow with millions of records. Pre-computing daily stats would make trend queries O(1) instead of O(n).
